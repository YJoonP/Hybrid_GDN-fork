# DFlash-b16 (전체 State 저장 롤백) — Qwen3.5-4B, RTX 3090 (GPU 0)

다른 롤백 방식(SpecLA, modeal, confk)과의 비교는 `results_compare/report.md`에 있습니다.

## 1. 핵심 결과 요약

- **batch 1**: 전체 State 저장 롤백의 DFlash-b16은 106.2 ± 0.2 tok/s입니다. AR 22.7 tok/s 대비 **4.68배**이고, τ = 6.22, TPOT = 9.4ms입니다.
- **batch 8**: 791.6 ± 0.5 tok/s로 **4.43배**입니다. 같은 GPU에서 잰 다른 롤백 방식(SpecLA 4.35배, modeal 4.24배, confk 4.12~4.17배)보다 빠릅니다.
- **batch 64·128**: snapshot 버퍼만 **52.7GB·105GB**가 필요해 할당 단계에서 OOM입니다. 같은 batch의 AR은 1225 / 1345 tok/s입니다.
- **롤백 비중**: 저장 + 복원은 decode 시간의 **2.4%(batch 1) / 3.1%(batch 8)**로, 비교한 방식 중 가장 작습니다. 복원은 수락 길이와 무관하게 스텝당 0.87ms입니다.
- **스냅샷 쓰기 비용**: recurrent 스냅샷 쓰기는 batch 8에서 스텝당 GPU 7.6ms입니다(보정 측정). 지금 엔진(HF eager)에서는 CPU 런칭 오버헤드에 가려 처리량에 드러나지 않습니다.
- **출력**: 다른 모든 롤백 방식과 256/256 동일합니다. AR과의 완전 일치율은 68.4%(batch 1) / 71.1%(batch 8)이고, 불일치는 bf16 동률 토큰입니다.

## 3. 분석

- **batch 증가에 따른 speedup**: 4.68배(batch 1) → 4.43배(batch 8) → OOM.
  - 검증 forward(스텝의 약 75%)는 batch 1·8에서 CPU 런칭 오버헤드가 지배해 토큰 수와 거의 무관합니다. 그래서 스텝당 6.2토큰이 그대로 이득이 됩니다.
  - batch 64라면 검증이 1,024토큰을 처리해 연산량 한계에 걸립니다. 다른 롤백 방식으로 잰 결과 0.92~0.98배였으므로, 메모리가 있었더라도 이득은 없었을 것입니다.
- **롤백 오버헤드**: 복원은 층마다 recurrent·conv 저장본을 한 번씩 복사하는 것이라 스텝당 0.87ms로 일정합니다. 재계산 방식(SpecLA 3.5ms, modeal 4.4ms)보다 4~5배 짧고, 이 차이가 방식 간 처리량 차이를 거의 그대로 설명합니다.
- **숨은 비용**: 16위치 스냅샷 쓰기는 batch 8에서 스텝당 6.4GB(GPU 7.6ms)입니다. 이번 측정의 verify 시간(29.7s)은 저장이 없는 SpecLA(29.5s)와 같았는데, CPU 오버헤드 밑에 가려졌기 때문입니다. CUDA graph를 쓰는 엔진에서는 이 비용이 드러나 batch 8 이상에서 fullstate의 우위가 줄거나 뒤집힐 수 있습니다.
- **메모리**: snapshot은 시퀀스당 0.82GB(24층 × 16위치 × (2.1MB + 49KB))입니다. 24GB GPU에서는 batch 8(6.6GB)이 실용적 한계입니다.

## 4. 결정 기록

`results_compare/report.md` §4에 전체 목록이 있습니다. 이 셀들에 직접 해당하는 것은 다음과 같습니다.

1. **SpecLA 재사용**: 시작 시 SpecLA 구현과 `results_specla/`가 없어 Phase 0~1을 새로 구현하고 AR을 새로 측정했습니다.
2. **DFlash 설치**: z-lab/dflash 커밋 07ebd93을 `--no-deps`로 설치했습니다. `dflash[local]`의 torch·transformers 버전 고정을 피하기 위해서입니다.
3. **블록 정의**: anchor + draft 15이고, 공식 정의와 같습니다. bonus 토큰은 다음 블록의 anchor입니다(공식 루프). 복원 위치는 anchor + 수락 draft 수입니다.
4. **위치별 State 저장 방법**: fused Triton 커널 한 번으로 저장합니다. 토큰 루프 대비 batch 1에서 35배, batch 8에서 8배 저렴합니다(`snapshot_method_bench.json`).
5. **KV truncate**: 확정 길이만 갱신하고, 뒤쪽은 마스크 후 다음 스텝에서 덮어씁니다.
6. **토큰 수**: 출력 128토큰에는 prefill이 만든 첫 토큰이 포함됩니다. decode 처리량에는 127개만 셉니다.
7. **warmup**: batch를 채운 decode 5스텝입니다. 보정 측정용 1스텝도 결과에서 버립니다.
8. **GDN 스냅샷 쓰기**: 커널 안에 융합되어 있어, 저장 비용은 셀마다 저장 있음/없음 커널을 비교하는 보정 측정으로 보고합니다.
9. **Phase 3 출력 검증 39/50**: 불일치는 모두 logit 1·2위 차이 ≤ 0.125인 동률 지점이고, 원인은 batch 비불변 커널입니다(cuBLAS M=1 GEMV, RMSNorm reduction 순서). State 검증은 통과했습니다(동일 입력 재계산 대비 오차 0). 사용자 승인으로 일치율을 기록하고 진행했으며(`phase3_override.json`), 원인 분석 근거는 `superseded/`와 `results_compare/report.md`에 있습니다.
10. **마지막 블록**: 16을 유지하고 확정 수만 자릅니다.
11. **GPU 기록 보충**: 이 폴더의 셀은 GPU 기록 필드를 추가하기 전에 실행됐습니다. 실행 래퍼가 `CUDA_VISIBLE_DEVICES=0`을 고정했으므로 GPU 0으로 보충 기록했습니다(`gpu_backfilled`).

## 5. 실패·OOM·이상치

- **OOM**: DFlash-b16 batch 64(snapshot 2GB를 할당하다 실패, 필요량 52.7GB), batch 128(필요량 105GB). 둘 다 할당 단계입니다.
- **AR batch 128 run1**: 1272 tok/s로 run2·3(1381)보다 8% 낮습니다. 표준편차 ±62.7에 반영돼 있습니다.
- **수정된 버그**: 처음 Phase 3에서 드래프트 블록 입력이 mask 토큰이 아니었습니다(τ 1.17). 수정 후 다시 검증했고, 수정 전 결과는 `superseded/`에 있습니다.
- **CUDA 초기화 간헐 실패**: `cuInit` error 3이 가끔 났습니다. 재시도 래퍼로 처리했고, 결과에는 영향이 없습니다.
